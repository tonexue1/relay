# Relay · 端侧模型与工具

> 状态:设计原则(2026-08-17)。
> 问题:端侧 3B 的 function calling 不可靠,"agent" 这个词还成立吗?
> 承接:orchestra 的 Call/Yield 见 [multi-agent-extracted.md](./multi-agent-extracted.md);spike 见 [spikes.md](./spikes.md)。

---

## 0. 结论先行

诚实讲:3B 的 function calling **不是"不能",是"不可靠,而且随工具数量和步数指数级崩"**。Qwen2.5-3B 在同级里算好的,但仍然:工具一多就选错、参数乱填、该调不调 / 不该调乱调、多步就漂。**它不是合格的"司机"。**

但这**不该由端侧模型当司机**——而这正是 edge-first 架构在替你挡的东西。关键:把两种被混为一谈的"用工具"拆开。

---

## 1. 两个桶,先分清

| | 模型决定的工具调用(agentic) | 代码发起的能力调用(pipeline step) |
|---|---|---|
| 谁决定调不调、调哪个 | **模型**(3B 的死穴) | **代码**(写死的编排) |
| 例子 | 助理自己决定"要不要搜一下" | 做梦:抽取→去重→写图,每步固定 |
| 3B 行不行 | 勉强、要重兜底 | **根本不需要模型决策** |

**核心一招:把尽可能多的活从左桶挪到右桶。**

看核心场景其实全在右桶:**做梦不需要 3B "决定调用写图工具"——代码去写图,3B 只负责吐三元组内容。** 检索、摘要、抽取,全是"代码调能力、模型填内容",压根不是 agentic tool calling。左桶那个难题,在记忆 / 做梦主线上**根本不存在**。

---

## 2. 真需要动态选工具时,按这个梯子降难度

从"别让模型做决策"到"实在要做就做到最小":

1. **GBNF 约束调用格式**(现成):强制模型只能吐合法 tool-call JSON。消灭参数乱填 / 结构崩——但只治格式,不治"该不该调"。
2. **砍决策面**:3B 死于"15 个工具 + 自由参数",活于"2–3 个 / yes-no / 填一个槽"。每步只暴露**一个**工具或零个。这正是 **Pipeline** 的意义。
3. **规划上移,执行留端**:tool use 最难的是**规划 / 选择 / 排序**。让**代码或云端**当编排大脑,3B 只做被指定的、grammar 约束的局部执行。端云分工套在工具上:云/代码是脑,端是手。
4. **把"函数调用"降级成"分类"**:真要动态(助理决定搜索 vs 直接答),别用 full function-calling,用**受限枚举的分类调用**("要不要工具?哪个?"选 A/B/C)。分类 3B 做得到,自由编排做不到。
5. **校验 + 修复环**:调用外面包 schema 校验 + 语义检查 + 便宜重试。用确定性护栏兜住不稳的生成器。

---

## 3. 这不是打脸,是给设计盖章

回看,我们**早就**为这条约束做了选择:

- orchestra **先做 Pipeline / Supervisor,不做 Swarm / GroupChat** —— 确定性编排把控制流交给代码,不赌 3B 自主。
- 做梦是**写死的 Pipeline** —— 模型零工具决策。
- **端云分工** —— 硬规划上云,端上只做 bounded 执行。
- **GBNF** 早就在武器库里。

**"端侧模型不会用工具"正是 edge-first 必须"重编排、轻自主"的根本原因**,而不是对愿景的威胁。谁在端上卖"给它 20 个工具自己 figure out"的自主 agent,谁翻车。我们卖的是**代码 / 云编排 + 端上受限执行**。

---

## 4. 诚实的边界

真正**开放式、多工具、多跳的自主 agent**,3B 不是司机——那种要么上云,要么不做。别承诺端上自主多工具编排。

---

## 5. 一句话收尾

**别让 3B 当司机。端上的"工具"绝大多数是代码发起、模型填内容,根本不需要它决策;剩下真要动态的,用 GBNF + 砍决策面 + 分类路由降到它能干的程度,硬规划上云。** 端侧模型不会用工具,不是 bug,是"重编排轻自主"架构成立的理由。
