# 多 Agent 小说生成器

用 `relay/memory` 的 ledger 合同做记忆层，七个角色协作写长篇。

记忆层是这个项目的地基，不是一个"顺便调用的库"。长篇生成最难的两件事——
角色知道了它不该知道的事、后面章节的信息漏进前面——在这里是数据库不变量，
不是 prompt 纪律。

---

## 为什么是这个架构

调研结论见下，三个已验证的做法被直接采用：

**director-actor-critic-narrator 四角色。**
[MAGNET](https://arxiv.org/html/2607.00918)（2026-07）在 100 页长度上比单模型
少 41% 编辑标注、少 50% 幻觉，比 IBSEN 少 34%/45%。关键不是"用了多个 agent"，
而是世界状态显式化：演员基于共享状态提议动作，critic 逐条判定并产出状态更新，
narrator 才合成散文。

**大纲分两层，细纲滚动重规划。**
[DOC](https://arxiv.org/pdf/2212.10077) 证明详细分层大纲比 Re3 的粗纲在情节
连贯性上高 22.5%——三句话的开头中间结尾撑不起长篇。但
[DOME](https://aclanthology.org/2025.naacl-long.63.pdf)（NAACL 2025）指出细纲
必须滚动规划，因为生成本身有不确定性。所以粗纲冻结一次，细纲只看未来一两章。

**质检分三层，但没有一层做风格重写。**
这是个反直觉的负面结果：DOC 明确砍掉了 Re3 的 editing 步骤，实测对最终质量
没有显著贡献。而 [MemAGent](https://doi.org/10.1109/iccvit67848.2025.11391379)
的 Generate-Reflect-Revise 又有 50% 连贯性提升。两者不矛盾——前者砍的是**风格
润色重写**，后者做的是**逻辑一致性检查**。所以三层质检都只管硬一致性：

| | 时机 | 看什么 | 调 LLM |
|---|---|---|---|
| L1 闸门 | 成文前 | 单个动作提议的机械违规 | 否 |
| L2 质检 | 成文前 | 单个动作提议的逻辑合理性 | 是 |
| 审校 | **成文后** | 整章正文对锚点的自洽 | 是 |

第三层是后加的，而且是被实测逼出来的。前两层都在【动作提议】那一层，可是正文
是叙述者拿着动作序列重新落笔的，这一步之后原本没有任何人再读一遍。真模型上
出现过叙述者凭空补出"出城半里、河边喝水、卖梨小贩"一整段，和"门已经开了一扇"
（上一章结尾门是关着的，动作序列里也没有开门这件事）——两类都不可能被前两层
发现，因为它们早在成文前就跑完了。

还有一条比"多写一段"更隐蔽：**记忆不从正文抽，从过闸的动作序列抽**。正文是渲染，
它多写出来的东西没过 L1/L2；从正文抽记忆，叙述者一加戏、加出来的戏就直接进了
账本，唯一的拦阻是审校——而审校因为 token 预算耗尽静默失效过一整轮。

审校**只挑刺、不改稿**，硬伤清单交回叙述者做定向修订。找硬伤是审校的强项，
落笔是叙述者的强项；让审校兼职改写的结果是改得太多、文风被改花。

**演员不写散文。** 文风归叙述者独占，否则一章里会出现好几种笔调。

### 跟 MAGNET 的差别

MAGNET 需要 ATLAS 事后把每个场景转成图、跨场景 diff 来**检测**幻觉。
这里两类主要幻觉在检索层就**不可能发生**：

| | MAGNET | 这里 |
|---|---|---|
| 未来信息泄漏 | 事后图 diff 检测 | `at` 硬过滤写在 SQL `LIMIT` 之前 |
| 跨角色视角泄漏 | prompt 约束 | `include_owners` 默认为空，跨 owner 恒零条 |
| 角色不知道自己在哪 | prompt 里塞状态 | 必带 State 点时直读，缺失 `Blocked` |

MAGNET 的 world state 是 `networkx.DiGraph`，但结构是 root → 角色节点 →
state key 节点，是星形状态存储、不做多跳推理。所以它等价于这里的
`state_field` 目录加按 owner 分仓的 STATE 项，跟"不建图"的决定不冲突。

## 架构

```
                  ┌──────────────────────────────────────────┐
                  │ Bible 设定（一次性，人工确认）              │
                  │ 题材 / 主角 / 世界规则 / 禁忌 / 结局方向     │
                  └────────────────┬─────────────────────────┘
                                   │ 种子 state_field + 初始 State
                                   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Planner 规划                                                          │
│   粗纲  幕结构 + 主线冲突 + 结局      ← 冻结一次                        │
│   细纲  只展开接下来 1~3 章的 Beat    ← 每章后滚动重规划                 │
│   Beat = {目标, 参演角色, 地点, 场次, 必须发生的事, 完成判据}            │
└────────────┬─────────────────────────────────────────────────────┬───┘
             │ 当前 Beat                          beat 达成 / 卡住 │
             ▼                                                    │
┌──────────────────────────────────────────────────────────────────────┐
│ Director 导演（唯一全知：include_owners=["世界"]）                      │
│   搭场（一场一次）：定 cast / 地点 / 场景目标 / 点名单                   │
│     为每个演员各发一次 recall（一次 recall 一个 ownerId）                │
│   调度（每拍一次）：下一拍谁动，或者收场；可插一句环境事件               │
│   判 beat（一场一次）：达成 / 继续 / 卡住，卡住就回 Planner 要新目标      │
└──┬───────────────────────────────────────────────────────────────┬───┘
   │ recall(ownerId=林晚, at=story_time, include_owners=[])         │
   │        required_fields=[location, current_goal, status]        │
   ▼                     ▲ 每拍回来问一次「下一个谁」                 │
┌──────────────────────────────────────┐                          │
│ Actor（一拍一个人，由导演挑）           │  只出 ActionProposal      │
│   persona + 必带 State + POV 记忆      │  {意图, 台词, 情绪,        │
│   + 本场已发生的公开动作（每拍刷新）    │   引用编号, 自述位置}      │
│   被问话的人该答，被逼到墙角的人该反应  │  不写散文                  │
└─────┬────────────────────────────────┘                          │
      │ 1 个 ActionProposal                                       │
      ▼                                                          │
┌──────────────────────────────────────────────────────────────────────┐
│ L1 ContinuityGate（机械闸门，不调 LLM，直接查库）                       │
│   引用   cites 必须在导演给的 citable 清单里 → 否则是凭空编造往事        │
│   位置   claimed_location 必须等于必带 State 的 location                │
│   在场   addresses 必须在本场 cast 里                                  │
│   角色   mentions 必须是设定里存在的人                                  │
│   违规 → 带着具体违规项打回重生成                                       │
└──────────────┬───────────────────────────────────────────────────────┘
               ▼ 通过
┌──────────────────────────────────────────────────────────────────────┐
│ L2 Critic 评审（LLM，只管逻辑不管文笔）                                 │
│   具体 ? 在人物性格内 ? 推进当前目标 ? 没越界 ?                         │
│   产出：接受 / 反馈重生成（上限 K 次）                                  │
│         + 建议的 State 变更 + beat 是否达成                            │
└──────────────┬───────────────────────────────────────────────────────┘
               ▼ 过闸的动作序列 ── 这是事实源，正文不是
┌──────────────────────────────────────────────────────────────────────┐
│ 场级落账（每场一次，必须在下一场开演前落）                              │
│ Chronicler 书记（LLM，读动作序列）→ Proposal，不能写库                   │
│ HostPolicy 宿主策略层（无 LLM）→ 裁决 → AuthorizedCommand              │
│   世界仓   客观 Episode（"沈砚被官兵带走"）                              │
│   角色仓   主观 Episode（"他又抛弃了我"）                                │
│   State    带 valid_from；闭集归一；抽取器无权写的字段直接挡回           │
│   Reflection  必须挂本场刚落地的 Episode 作证据，无据只能 CANDIDATE      │
│   新字段   抽取器提的新名先占槽，只能 CANDIDATE，等作者确认              │
└──────────────┬───────────────────────────────────────────────────────┘
               ▼
        ┌───────────────────────────────┐
        │ Memory Ledger (SQLite)         │  ← 下一场的演员从这里读
        │ at=STORY_TIME 硬过滤在 LIMIT 前 │     所以不能攒到章末落
        │ owner 隔离 = SQL 保证           │
        └───────────────────────────────┘

       ═══ 本章全部 beat 演完之后，才走下面这一段 ═══

┌──────────────────────────────────────────────────────────────────────┐
│ Narrator 叙述者（唯一决定文风，一章一次调用，不许新增事件）               │
│   输入是整章的分场动作序列 + 风味卡全部七面 + 章间承接锚点               │
│   一次落笔，所以章内不存在"两段各自生成的正文接不上"这种缝               │
└──────────────┬───────────────────────────────────────────────────────┘
               ▼ 整章初稿
┌──────────────────────────────────────────────────────────────────────┐
│ Reviewer 审校 ⇄ Narrator 定向修订（反射循环，默认 2 轮，章级）           │
│   依据用的就是叙述者拿到的那一份分场渲染（同一份，不重新拼）              │
│   立锚点（时空 / 人物 / 事实）→ 逐段扫描 → 硬伤清单 JSON                 │
│   只挑刺不改稿；叙述者按清单打补丁，输出整段（补丁模式抄不准原句）        │
│   护栏：修订稿骤缩到不足 50% 判为截断，弃用保留上一版                    │
│   审不出（解析失败/超时）→ 按通过兜底并报出来，不崩、不误判              │
└──────────────┬───────────────────────────────────────────────────────┘
               ▼ 审过的稿 → 落库为「已发表正文」（承接锚点只读这一类）
        ┌───────────────────────────────┐
        │ Titler 起标题（读整章正文）      │
        └───────────────────────────────┘
```

两段式，跟 wuxia-novel 同形：**多智能体演戏求"意外"，单智能体成文求"连贯"**。

* 每场：`Director 搭场 →（每拍：Director 点人 → Actor → L1 → L2）→ 判 beat
  → 动作序列落成状态和记忆`
* 每章：`全部场演完 → Narrator 一次落笔整章 → Reviewer ⇄ Narrator → 正文落库 → Titler`

事实和正文刻意是两条线：事实必须**场级**落，因为下一场演员开场要读上一场写的
状态；正文必须**章级**落，因为一场一次落笔会留下真实的接缝。而事实源取的是过闸的
动作序列，不是正文——正文是渲染，它多写出来的东西没过 L1/L2。

Planner 只在 beat 达成或卡住时唤醒。

### 谁能读什么

| 角色 | owner | include_owners | 能看到 |
|---|---|---|---|
| Planner | — | — | 导演喂的世界线摘要 + 各角色状态 |
| Director | 世界 | — | 世界仓全部客观事实 |
| Actor | 自己 | 空 | 只有自己仓里 `at` 之前的记忆 + 本场已发生的公开动作（每拍刷新） |
| L1 Gate | — | — | 导演实际交给该演员的清单 |
| Critic | — | — | 该演员的 brief，不含全知信息 |
| Chronicler | — | — | 一场的动作序列（**不是正文**） |
| Narrator | 世界 | — | 整章的分场动作序列 + 章间承接锚点 |
| Reviewer | — | — | 与叙述者**同一份**依据，外加待审的整章正文 |

## 对照锚点

审校能不能审出硬伤，取决于它手里有没有一份可信的基准。没有基准的审校只能凭
语感挑刺，那还不如不审。所以四类锚点全部从账本查出来，不是让模型"回忆"：

| 锚点 | 治哪类错 | 怎么来的 |
|---|---|---|
| 上一章结尾（逐字，取尾 400 字） | 章间复述、时点接不上 | `recent_raw_events(before=at, role=已发表正文)` |
| 已故名册 | 死人开口 | `status ∈ death_states` 点时读 |
| 关键物品归属 | 同一件东西同时在两个人手里 | 数组字段按 owner 渲染 |
| 各人此刻所在地 | 隔着半座城对话 | `location` 点时读 |

承接刻意用**逐字原文**而不是检索摘要：摘要丢掉的正是"上一段最后怎么收的"。
只取尾部而不是整章，因为整章喂回去会诱使叙述者复述。

承接是**章间**的，不是场间的：正文一章落笔一次，章内没有接缝需要缝合。那个缝
原本是"一场一次落笔"自己造出来的。

回读要按 `role` 筛。世界仓下同时存着两类原文——已发表正文和过闸的动作序列——
不筛就会拿一串「林晚：把针搁回绣绷」去当上一章的语气承接。

修订时锚点要额外标"判对错用，勿抄入正文"。不标的话，叙述者会把锚点里提到、
而正文原本没有的道具和称呼一路搬进正文——定向修订就变成了扩写。

## 风味卡

文风原本只有 Bible 里一句 `style`，而且只有叙述者看得到。结果是规划的节奏、
导演的场面调度、叙述的笔调各走各的——文风只在最后一步生效，前面两步已经把戏
搭成了另一种气质。

风味卡（`styles/<id>/card.json`）把文风拆成七面，按需要投给三层：

| 层 | 拿到什么 |
|---|---|
| Planner | `tagline` + `setpiece` + `hook`：决定章末留什么钩子、大场面怎么顶 |
| Director | `direction.scene` + `avoid`：决定场面的格局和取景 |
| Narrator | 全部七面（+ 第 1 章加 `direction.opening`），按强度档位调遵循力度 |

刻意不放示范段落，只放抽象技法：喂样例会让模型往样例的具体情节上靠。

`lexicon_terms` 是给离线计分卡数命中用的显式词表。从 `lexicon` 那段散文里抽词
只能抽出"偏爱苍茫"这种半截词，所以让卡自己报准数。

内置 `baimiao`（白描）和 `gulong`（古龙式）。换卡：`--style gulong`。

## 故事时钟

业务时间必须比"章"更细。一章有多场戏，一场戏内部还要分"场前读取"和
"场后落账"，否则本场写的状态会被本场自己读到，等于让演员提前知道
自己接下来要做什么。所以章占百位，场占十位，场内偏移占个位：

```
第 0 章（Bible 初始状态）   = 0
第 1 章第 0 场   场前读取   = 100
                 场中变更   = 101   critic 判定过的 State
                 场后落账   = 102   Reflection
第 1 章第 1 场   场前读取   = 110
第 1 章章末                 = 199
第 2 章第 0 场   场前读取   = 200
```

## 跑起来

```bash
pip install -r requirements.txt
cp .env.example .env        # 填 NOVELIST_API_KEY
```

默认配的是 DeepSeek。规划和落笔走 `deepseek-v4-pro`，演员、质检、书记走
`deepseek-v4-flash`——这三个角色调用最频繁，而且做的是结构化判定不是创作。
旧的 `deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 下线，别再用。

三个 DeepSeek 特有的坑，`.env.example` 里已经处理了：

**思考 token 也算输出。** JSON 模式下 `max_tokens` 给少了会截断成坏 JSON。

**审校要单独给预算。** 它得先写审查清单再吐硬伤 JSON，篇幅是别人的几倍。给统
一的 8192 会写到一半被截断，末尾的 JSON 永远出不来，然后被"审不出、按通过兜底"
静默放过——看上去像审校很宽松，其实是根本没审。所以有
`NOVELIST_MAX_TOKENS_<ROLE>` 按角色覆盖。

**审校也该关思考。** 它的 prompt 已经要求把审查过程写成正文，那就是它的推理；
再开原生思考等于同一件事付两遍钱，还跟正文抢同一个输出预算。同理，抽取和判定
类角色开思考只是变慢变贵。统一用 `NOVELIST_THINKING_DISABLED_ROLES` 关掉。

产出落在 `out/`：`chNN.md` 是正文，`novel.db` 是记忆仓，`scorecard.md` 是计分卡，
`trace.jsonl` 是 LLM 流水。**离线跑单独写 `out/offline/`**，不跟真跑共用目录——
假模型产出是烟雾测试的副产品，真跑产出是成品，共用一个目录的话一次
`--offline --fresh` 就把成品冲没了，而且没有任何提示。

```bash
# 离线跑通，不花钱。验编排、闸门、记忆读写，不验文笔。
python run.py --offline --fresh

# 接真模型
python run.py --chapters 3 --fresh

# 换风味卡，调审校轮数
python run.py --chapters 3 --fresh --style gulong --intensity high --review 3

# 看记忆仓里存了什么
python run.py --inspect

# 离线给已生成的章打分，不花钱
python run.py --verify

# 落盘每一次 LLM 调用（out/trace.jsonl）
python run.py --chapters 2 --trace

# 把流水读成人话
python run.py --trace-report
python run.py --trace-report --grep REVIEWER
```

`--trace` 是唯一能看清"审校到底审了没有"的手段。上面那个静默失效的坑就是靠它
挖出来的：日志显示"审校第 1 轮 → 通过"，流水里却是空响应加
`finish_reason=length`。

`trace.jsonl` 是**一次调用一行**（不是一章一行），单行几千字符，肉眼没法读，
所以配了 `--trace-report`：

```
51 次调用，合计 647 秒

  NARRATOR      4 次     350 秒  均  87.6 秒
  PLANNER       3 次     232 秒  均  77.3 秒
  DIRECTOR     14 次      15 秒  均   1.0 秒
  REVIEWER      4 次      14 秒  均   3.6 秒
  ...
  没有截断，没有空产出。
```

按总耗时排序，因为要回答的是"谁在吃时间"。这份输出说明两件事：墙上时间的 90%
花在叙述者和规划这两个 `pro` 角色的 7 次调用上，压时长该动它们而不是减少调用
次数；以及审校关掉思考之后平均 3.6 秒，比叙述者快二十多倍，这一层加得很便宜。

`--inspect` 的输出直接反映记忆层是否在干正确的事：

```
== 世界线（客观） ==
  [101] 第1章：林晚、周娘子当面把事情摊开了。
  [201] 第2章：林晚、周娘子当面把事情摊开了。

== 林晚 ==
  current_goal = 把这次问出来的话走到底
  location = 临安
  status = 疲惫
  affiliation: MISSING            ← 缺失是显式报出来的，不是静默空值
  [101] EPISODE 第1章，我在场，我把话说出口了。
  [302] REFLECTION self_model：第3章之后，我不再指望别人先开口。
                               ↑ 只有最新一版是当前值，前两版已闭窗
```

## 离线计分卡

`--verify` 不调 LLM，只做确定性打分，所以能当回归用——改了 prompt 想知道有没有
改坏，跑一次就有数，不必再花一轮生成费用去人肉读。

```
《林晚》计分卡　2 章　风味：白描
总分 0.86
  标题不重复  1.00      章标题不许撞
  世界观落地  0.73      设定里的专名有没有真的写进正文
  风味贴合   0.58      风味词命中 + 短句占比落在卡声明的区间
  去套话    1.00      "心中一凛""不禁""仿佛整个世界"这类套话计数
  账本连贯   1.00      ↓
```

最后一项是**其他工具做不到、而这里近乎免费**的部分：账本能做点时读取，所以能
拿正文去对"那一章当时"的事实，而不是拿现在的事实去对过去的章节。三类命中：
死人开口、道具串门、隔空同框。

两条降噪规则都是拿真产出试出来的，写下来是因为不写就会退化成噪音：

**先剥对白再找人名。** 周娘子说「那沈砚要是真心」，沈砚人在洛阳，按名字直接
匹配就报一条"隔空同框"——可他只是被人提起。降噪前 4 条命中全是这类误报。

**隔空同框要求章首章末都不同地。** 有人在本章赶路的话，章首必然两地，而那正是
这一章要写的事。只看章首会把每一次旅行都判成硬伤。

### 它实际做过的一次决策

把成文从场级改成章级时，拿同一本 Bible 各跑 2 章对比：

| | 场级成文 | 章级成文 |
|---|---|---|
| 总分 | 0.79 | **0.86** |
| 账本连贯 | 0.75 | **1.00** |
| 世界观落地 | 0.64 | **0.73** |
| 风味贴合 | **0.75** | 0.58 |
| 正文字数 | 1518 | 1686 |

风味贴合是退的，而且不是篇幅造成的（新版更长）：叙述者调用从 4 次降到 2 次，
风味卡的注入次数跟着腰斩，每单位篇幅的文风强化就少了。这是这次改动**明确的代价**。

但真正说明问题的不是总分，是顺手查出来的一件事：场级那一版里，`林晚` 的
`location` **整轮没变过**，一直是种子值"临安"，而正文里她已经走到洛阳了。那条
"隔空同框"命中不是误报，是在报"账本停止跟踪她了"。章级那一版有完整的版本链
（临安 → 途中 → 洛阳，各带 `valid_from/valid_to`）。

单次对比、两轮的大纲还不一样，所以分数只能当方向看。但"状态有没有在推进"是能
直接查的，不用靠打分。

## 已知边界

**没接向量。** 四路检索里向量通道要宿主注入 embedding，目前没接，所以
`index_health().vector_available` 是 False。FTS + Recent + Tag 三路照常工作，
这本身也是合同要求的降级行为。

**Reflection 的证据只挂本场 Episode。** 跨章累积的证据链没做。

**L1 闸门只查四类。** 时间线一致性依赖记忆层的 `at` 过滤，闸门自己不重复查；
物理连续性（上一场在洛阳这一场不能在临安）没做。

**拍级调度的代价是导演调用变多，但便宜。** 实测 2 章：导演调用 14 → 22 次，只多花
13 秒；而叙述者从 4 次 × 88 秒变成 2 次 × 153 秒，审校从 4 次变 2 次，总墙钟
647 秒 → 564 秒。多问导演的钱是省下来的。搭场仍然一场只做一次——那里含每个演员
一次 POV recall，按拍重搭既贵、又会让演员的"已知"在一场之内漂移。

**导演收场和 beat 判据可以不一致，此时按收场处理。** `next_actor` 管节奏，
`judge_beat` 管"判据走完了没"，两者会合法地打架：实测 4 个 beat 里有 2 个是导演
说收了、判据判 CONTINUE（理由是"城门尚未合上""未确认她未回头"这类字面残留）。
拍级调度下收场归导演，所以**不回去补演**，但不一致会打进日志——不报的话
`CONTINUE` 就是个悄悄被丢掉的信号，看日志的人会以为它还有作用。

**`max_beats` 别往上调。** 默认 5。设 8 时实测两个 beat 都顶到上限、导演一次
`end` 都没说过，一章攒出 16 个动作，叙述者被要求一次写三千多字——8192 的预算在
思考型模型上被推理吃光，正文一个字没吐（`finish_reason=length` + 空产出），连试
三次后整章报错。三处一起改掉了：上限降到 5、篇幅加 `max_chapter_length` 封顶、
叙述者单独给 `NOVELIST_MAX_TOKENS_NARRATOR=16384`，并在临近上限时提醒导演收场。
顶到上限现在会打进日志。

**审校是章级的，没有跨章审校。** 一章一审，所以章内的重复和接缝审校看得见了；
但跨章的伏笔回收、跨章重复仍然没人管，只有计分卡能给个相对信号。

**章级成文换来连贯，也换来更长的单次输出。** 一次要写完整章，截断风险和审校的
预算压力都比场级高。审校已经因为预算耗尽静默失效过一整轮，所以它有独立的
`NOVELIST_MAX_TOKENS_REVIEWER` 和 `finish_reason` 落盘；`--trace-report` 会把
截断和空响应直接标出来。真要拿这条判断，用计分卡对比两种粒度，不要凭感觉。

**`location` 是闭集，且抽取器无权写。** 这两条约束都是被真跑逼出来的：自由文本
会写出"洛阳·府衙外·石阶"和"门内"，同一个地方两种写法，把 L1 的位置冲突检查、
锚点里的所在地、计分卡的隔空同框一起打瘸；而抽取器只能事后从正文里猜地点，它
猜错过——最后一场没人移动、质检没提，它就自作主张把两个人都写回了临安，其中
一个人根本没离开过洛阳。

地点的权威是质检，因为质检看得见动作。约束下沉到账本的 `allowed_writers` 和
`ValueContract.enum` 里，不靠再加一条 prompt 规则。代价是换故事得在 Bible 里
声明地点闭集，跨城市的粒度得自己定。

**计分卡的连贯性检查是相对信号，不是硬失败。** 人名出现不等于人在场，剥对白只
能挡掉一部分。数字变大就该去看一眼，不该拿它当门禁。
